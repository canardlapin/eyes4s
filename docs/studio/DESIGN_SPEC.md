# Eyes Studio — UI design spec (round 2)

Round 1 was reviewed by four critics (science 5, interaction 6, visual 6, buildability 5; all
REVISE). This spec is the round-2 contract. **All numbers come from FIXTURE.md / fixture.json**
(generated by make_fixture.py). Never invent a count, a mean, a time estimate, a memory budget
or a hash; if a value is unknown at that moment, show the honest state ("counting…").

## 1. Product thesis (unchanged)
"Result → comparison → gaze → fixation → source record, and back." Measured quantity:
matched-minus-control spatial similarity: per query q and scale σ, M = cosine(map q, map matched
reference); B = mean cosine to every eligible control; D = M − B. Keep M, every control score, B
and D. It measures spatial correspondence, not sequential replay. D mixes item-specific
reinstatement with shared item-driven salience and residual centre bias; say so wherever D is the
headline. No inferential statistics in the MVP.

## 2. Perspectives (app-owned; one scaladock Dock per perspective in a StackPane)
Data ⌘1 · Explore ⌘2 · Analysis ⌘3 · Compare ⌘4 · Figures ⌘5
- Data: sources, column mapping, trial identity, geometry, admission.
- Explore: look at trials, fixations, time, source records. View-only.
- Analysis: the recipe/draft, resolved design, preflight, run. The only place that edits
  science (plus Data geometry/admission, which make a new DATASET revision).
- Compare: results. Two layouts in one perspective, chosen by the trail depth: Summary
  (study → participants) and Query (query → pair → maps). "Summary" crumb shows the summary
  layout; any deeper crumb shows the query layout.
- Figures: figure composer and export.
Why separate Docks: `Dock.load` disposes panes missing from a layout, so switching one Dock would
destroy views. A studio pane registry provides singletons ("one Query panel") and floating
windows of an inactive perspective are hidden.

## 9. Science rules that must be visible
- Analysis window = image frame 1024×768 inside the 1920×1080 screen. Gaze outside the window is
  excluded from the map and REPORTED: per trial "outside window: 2 of 12 fixations · 9% of
  duration" (Inspector, Pairs table); a Reporting filter; a methods sentence.
- Initial fixation policy (Analysis field): "Keep all" / "Drop first fixation" / "Drop fixations
  within 1.5° of the cross before first saccade", with a count; applies to queries and references.
- Grid 64×48 on the image frame → cell 16 px = 0.46°. Show cell size next to Scales; warn
  when σ < 2 cells (0.5° ≈ 1.1 cells) and when σ makes maps near-uniform (8° ≈ 280 px on a
  29°×22° image).
- 35 px/° is DECLARED, not calibrated; linear conversion; shown with viewing distance/screen
  size fields in Data.
- Display kinds: Image · Blank · Blank + fixation cross · Cue · Unknown · Missing asset (hatched).
  Retrieval here = "Blank + fixation cross". Remembered-image underlay off by default and, when on,
  labelled "Reference image — not displayed during this trial".
- Recognition preset: lures/novel probes get "No corresponding study trial (by design)", a
  category separate from data-error "no match", in every count strip. A known category with no
  admitted members shows 0; an unavailable category shows n/a. An unadmitted focal trial
  belongs to the unadmitted count, so the four query categories remain a partition.
  With an explicit expected-unmatched selection, an unselected query whose reference
  is absent from the supplied inventory is "no match", not "by design". In particular,
  an observed-only export cannot turn an old probe's undeclared study trial into a lure.
  Without an explicit selection, the existing inventory-only design convention applies.
- Duplicate references: eyes4s preflight reports DuplicateTrial as a Warning; ByLeft reduction
  would AVERAGE two matched pairs. A "Studio check" (labelled as such, not eyes4s) blocks the run:
  "Matched cardinality ≠ 1 for 5 queries — choose occurrence".
- Exact eligible counts exist only after paging the design (PairPage.Done): show "counting…" with
  a progress state until then; before paging show only the candidate pair count.
- Pairing eligibility does not promise a scored contrast. The resolved-design preview separately
  reports eligible focal trials with a library-known preparation failure (frame disagreement,
  no fixation kept, no fixation in the window, or a failing off-window policy) and those without
  one. Show their served per-trial reasons. Before execution, call the latter "without a known
  focal preparation failure", not "contributing": reference failures and later numerical failures
  are still possible. The fixture's 457 eligible queries split 454 + 3; its 454 contributing
  contrasts are an execution result, even though the fixture's totals happen to agree.
- For a smaller control pool, name declared reference candidates that admission did not admit,
  with their dispositions, as served by the library for the pairing's participant/item/occurrence
  rules. Do not call their count a number of lost pairs: another admitted occurrence can substitute
  under First/Last, and sampling can omit a reference independently of admission.
- Identity: show "input digest sha256:9f2c…e41 · plan rev 5", never an invented fingerprint.
- Reporting: participant means, equal weight; per-group n; paired n; the unit is the query trial.
  Automatically inferred categorical levels come from the declared focal-phase inventory,
  before admission, scoring and reporting filters. Reference-only attributes do not declare
  query groups. Genuine empty focal groups retain their cells and absence reasons.
- Say "record" (fixations.csv record 7,214), not "row". Show raw and transformed coordinates.
- Import requires the Participant, Phase and Trial roles (the trial key eyes4s reads), the Ordinal
  and Sample-count roles, x, y, Onset and Duration; time units are DECLARED (ms), never inferred.

## 10. Keyboard and accessibility
Each plot/trial view is ONE focusable node with a roving cursor (arrow = nearest mark in that
direction via the picking plan; Enter = select → selection bus; Esc clear; Tab leaves). Show a
focused mark with a 2px accent ring. F6 cycles panes; ⌘⇧↩ maximizes the focused group. Every
plot has a synced Table tab.

Results derives its complete focus order from served view-models and plot/table cursor
state. A served plot or table owns the focus stop; its dock container is not an additional
stop. An unread or empty pane retains a reachable container. The Participants navigator
keeps one composite stop with its current row announcement. Scale selection and Explain
remain distinct controls. F6 enters the content that owns a pane's focus, and Ctrl+Tab
reaches its sibling table. Responsive plot annotations remain in the full announcement.

### Window size

The reference boards and initial window are 1440×900 logical pixels. The supported
small-window scene is 1024×656 logical pixels, matching the constrained native macOS
qualification display. The work area keeps at least 1280×864 logical pixels and scrolls
when the window is smaller; larger windows expand it normally. This preserves useful
space for map frames, wrapped captions, plot axes and annotation columns without
requiring an OS window larger than the display. Scroll bars expose the entire work area,
including its header, inspector and status controls. The viewport adds no Tab stop.
Tab, Shift+Tab, F6 and Ctrl+Tab reveal the focused control after layout settles; a composite
larger than the viewport reveals its cursor row, or its leading edge when no row is active.
Home, End and arrow navigation keep that row visible through both nested and outer clips.
Pointer drags continue to belong to plots and dock dividers. Small-window evidence is
readability and reachability evidence; the 1440×900 Linux pixel court stays separate.

## 13. Owner decisions 2026-09-26: portability and off-screen gaze

**Portable by construction.** Ship on the JVM with JavaFX, but structure the app so that a
future UI technology (Electron or Tauri with Scala.js, or a browser) can be added without
rewriting behaviour. Rules:

- **Layers.**
  - `studio-core` (document, commands, revisions, services, `StudyBackend`), `studio-app` (the
    UI-neutral presentation layer) and `studio-viz` (Intaglio scene builders) are cross-built
    for JVM and Scala.js. CI links them for JS on every PR.
  - `studio-desktop` (JavaFX, scaladock, Intaglio's JavaFX backend, JVM platform services,
    packaging) is the only JVM-only UI layer.
- **Elm-style presentation.** `studio-app` owns the app model, the intents (user actions), the
  pure `update`, and the view-models every screen renders: perspectives, the trail, selection,
  freshness, banners, form state, table rows, formatted strings. A UI shell renders view-models
  and dispatches intents; it holds no behaviour. Every user-visible behaviour has a headless test
  at the `studio-app` level.
- **UI-neutral layout.** Perspectives and pane layouts are declared as a `LayoutSpec` in
  `studio-app`. `studio-desktop` maps them to scaladock, and a web shell would map them to a web
  docking library.
- **Platform services behind interfaces:** file system, project store, dialogs, clipboard, fonts,
  scheduler/clock, and external open. JVM implementations live in `studio-desktop`.
- **Serializable backend protocol.** `StudyBackend` requests, responses and progress events have
  cross-built codecs. There are two transports: in-process (JVM today, Scala.js later, since the
  eyes4s plan, codec and fs2 modules cross-build) and an IPC sidecar (a web shell calling a JVM
  backend). One conformance suite covers every transport.
- **One token source.** It generates JavaFX CSS, web CSS variables and Scala constants. Strings
  come from resource bundles owned by `studio-app`.
- **Enforcement.** The boundary check fails if `javafx.*`, `scaladock.fx`, `java.io` or `java.nio.file`/`java.nio.channels`
  appear outside `studio-desktop` and the platform implementations (`java.nio.ByteBuffer` and `java.nio.charset` are portable and allowed), and `cats.effect`/`fs2` in `studio-app` and `studio-viz`. The port contract is written
  up in `docs/studio/PORTING.md`.

**Off-screen fixations.** A finite fixation outside the screen does not quarantine its trial by
default. The configurable `OffScreenPolicy` is `ExcludeRecord` (the default) or `QuarantineTrial`;
changing it is a "Dataset · re-admit" change. Excluded records are reported under their own tally
and cause, "outside screen", separately from "outside window", and the methods text cites the
policy. Non-finite or unparseable coordinates still quarantine as before.

**Control pool with repeated references.** The occurrence selection used for the matched
reference also applies to the control pool, so each other item contributes one reference per
participant. "All occurrences as controls" is a named option that is never the default.

## 14. Token amendments from implementation (S1.1, 2026-09-26)

The contrast suite found four places where the board values break this spec's own rules (text
≥ 4.5:1, marks ≥ 3:1). The generated tokens take precedence over the boards:

- **Mid stage.** It is `#767676` with a white `--on-stage` (4.54:1, L* ≈ 50). White on the board's `#808080` was 3.95:1.
- **Halo.** `--halo` is a stage token. It is white on the dark and mid stages and ink on the light
  stage. A white halo on the light stage was 1.12:1, and dark-theme query marks were 1.35:1.
- **Control fill.** Light `--control-fill` (`#D98A1C`) is drawn only inside a `--control` outline,
  never as a bare mark on chrome surfaces, where it reached only 2.3–2.7:1.
- **Focus ring on the stage.** It is cased with the halo, the same way as the isolines.

Paper tokens for figures (`--paper`, `--paper-ink`, `--paper-ink-2`, `--paper-rule`) and isoline casing tokens (`--isoline-case`, `--isoline-ink`) come from the same source.
Open: the figure palette's control colour (`#D98A1C` on white paper, 2.76:1) is resolved in S9.2b,
and the colour lint does not yet catch named CSS colours or `Color.*` constants.

**Font weights in JavaFX (S1.2).** JavaFX picks a static face by family name. It does not use
`-fx-font-weight`. Weights therefore use the legacy family names from each face's name table:
"IBM Plex Sans Medm" and "IBM Plex Sans SmBld", "IBM Plex Mono Medm", and "Source Serif 4 Semibold".
The type lint rejects `-fx-font-weight` and `FontWeight` in studio sources.

## 15. Design hill climb amendments (owner decisions 2026-10-11, override anything above)

The boards in `design/` were revised in a scored review (baseline 6.34 → accepted 8.28 of 10; four
reviewers per round: visual, function and accessibility, science, JavaFX build). Where a board and
the desktop disagree, the desktop rule below stands, and `PARITY_CHECKLIST.md` records each open
deviation with its ticket.

- **Map alpha floor (§6).** A mass-map cell's alpha rises linearly from 0 at zero mass to 1 at 10%
  of the colour-limit range (`alpha = min(1, t / 0.10)`, t the fraction along the limits). The colour
  is unchanged and the one global map opacity (0.6) still applies. Coverage is shown by the frame
  outline, so the stimulus and stage show through low-mass regions. Mass maps only: difference maps
  stay opaque (zero sits mid-ramp). Missing cells are never transparent and never a ramp colour:
  they carry the missing-asset hatch, and the caption gives their count (missing ≠ zero).
- **Selection is a fill; focus is a ring.** Selected rows and items take the themed `--sel-fill`
  (light `#E4E0D6`, dark `#2E3035`) and weight 600 (Sans; selected Mono stays 500, the heaviest
  Mono face). Keyboard focus is the 2 px accent ring; focused and selected shows both. Hover uses
  `--surface-2`, so hover never reads as selection. On stages, marks keep the two-band `--sel-ring`
  (§4) and the focused mark gets the accent ring outside it.
- **Composite focus.** A list, tree, grid, plot or stage is one tab stop. While it holds keyboard
  focus its cursor item draws the accent ring (cased with the halo on stages) and the container
  draws none; the focused group's tab carries the accent top rule. The cursor ring shows only while
  the composite has keyboard focus (`:focus-visible`), and a composite with no items shows the ring
  on the container. Selection persists without focus. In JavaFX, `:focus-visible` rules come after
  `:selected`/`:armed` rules, and selected-and-focused is written as a compound rule.
- **Disabled and pending.** A pending or blocked action (for example "Save & run" while preflight
  is pending) is disabled and stays fully readable: opacity 1 and normal contrast
  (`PreflightFxSuite`). Its reason is visible next to it and attached to it for assistive
  technology. Any remedy or progress is a separate enabled control ("Cancel waiting"). Only
  controls with no workflow meaning fade to opacity 0.4.
- **Stage casing.** `--halo` stays a stage token (§14). Where a focus or role mark falls below 3:1
  on a stage with both mark and casing, it gets its own contrasting inner casing; it does not invert
  the halo. Tested in both themes on all three stages over map and image grounds.
- **Weights.** Sans 400, 500 (button, tab and segment labels only), 600; Mono 400 and 500; the hero
  number 500. No Mono 600 and no Sans 700.
- **Greyscale proof.** Figures' greyscale proof is a Rec. 709 relative-luminance render in linear
  light, not desaturation, so that match and control print as different greys.
- **Figures.** Participant and scale-profile plots label their numeric y ticks and print signed
  values. The fixation cross is a 20 px half-arm in native screen coordinates.
- **Geometry density.** Every occupied cell is drawn (the 5% share floor hid most outside-frame
  records). Levels step by record count and are fixed for one dataset revision, never rescaled per
  view; the level rule is §15.1.
- **Paired descriptive (Results).** "Δ Remembered − Forgotten" is the mean over participants of
  each participant's mean Remembered D minus mean Forgotten D, computed before rounding participant
  means: +0.18 (range +0.04 P15 to +0.34 P11; higher in 24 of 24). It is descriptive only, and the
  headline notes that it differs from the difference of the rounded group means by rounding.
- **Outside-window wording.** Geometry: "543 of 11,520 source records outside the window in 409
  trials". Methods (as `MethodsText` writes it): "543 of the 11,311 fixation records of admitted trials
  (4.8% of their fixation duration)". All 543 lie in admitted trials.
- **Science values.** The executable golden fixture (`fixtures/studio-golden`) is authoritative;
  the mock (`fixture/make_fixture.py`) is reconciled to it, and anything a board draws that neither
  contains is tagged "illustrative".

### 15.1 Placement density levels (review ticket 23)

The Data perspective's "All trials overlaid" density (`DensityPicture`, drawn by
`GeometryScene.density`) bins every placed record of a dataset revision on the backend's screen
grid: 64 columns, rows = round(64 × screen height / screen width), so 64 × 36 cells of 30 × 30 px
on the 1920 × 1080 screen. This grid is not the 64 × 48 map grid of §9. Counts are records, one
per placed record, with no smoothing and no duration weight; an off-screen record falls in no cell.
The owner settled this rule's four choices on 2026-10-12: the median-anchored step, the closed-range
key labels, the default key for an empty study, and the unchanged ramp for level 1 on the Mid and
Light stages. The levels are:

- **Count.** A cell's count is its whole number of records: the backend's count rounded half up,
  and at least 1 when the backend's count is above zero. A cell with count 0 is empty and is not
  drawn. Every other cell is drawn. There is no share floor.
- **Anchor.** `m` is the median count of the revision's non-empty cells, taking the lower middle
  value when there is an even number of them (the ⌈n/2⌉-th smallest of n). `m` is a whole number
  of records, so it needs no rounding.
- **Step.** `s` is the power of 4 nearest `m` on a log scale, at least 4: the largest `s = 4^j`
  with `j ≥ 1` and `s / 2 ≤ m`, else 4. A tie (`m = s / 2`) takes the larger step. This uses only
  integer comparisons. Snapping to a power of 4 keeps the key's labels round, and a correction that
  moves the median within its band (m from 1 to 7 for s = 4) leaves the levels unchanged. The
  owner chose this anchored step over fixed steps of 1, 4, 16 and 64 for every study (2026-10-12).
- **Thresholds.** Four levels start at 1, `s`, `4s` and `16s` records. A cell's level is the
  highest level whose start it reaches. Level 4 is the overflow level and has no upper bound. The
  levels use ramp stops 0 to 3 (§6), drawn opaque (see "Contrast"). Because the lowest start is
  always 1 and `s ≥ 4`, a cell holding one record is always at level 1. A singleton is never
  hidden, never merged with empty cells, and never shares a level with a cell of `s` or more
  records.
- **Fixed per revision.** The levels are computed once, in `DensityPicture.of`, from the whole
  grid of the shown revision: every placed record, including records of quarantined trials. They
  are never recomputed from a selection, a marked or focused trial, the stage, or the size of the
  drawing. `DensityPicture` carries the four starts, so the cells, the key and the semantics text
  read the same numbers. A new revision (a geometry, mapping or admission change, §8) gets its own
  levels, and its key shows them.
- **Key.** The key is the caption "Records per cell, log steps · {c} × {r} screen cells" and four
  swatches, ramp-0 to ramp-3, opaque, over the current stage. A swatch sits on the stage, so it
  takes the stage ground's rule (see "Contrast"): where its level is cased against the stage, the
  swatch wears that band as a 1 px border outside it. The view-model carries the stage and each
  level's band (`DensityKeyVM`), so the swatches change with the stage, and a stage change redraws
  the density. They are labelled with closed
  count ranges, `1–(s−1)`, `s–(4s−1)`, `4s–(16s−1)`, and the overflow as `≥16s`. Counts use
  thousands separators. For s = 4 the labels are "1–3", "4–15", "16–63", "≥64". The key always
  shows all four swatches, including a level that holds no cell. The owner chose these closed
  ranges over lower bounds ("≥1, ≥4, ≥16, ≥64") on 2026-10-12, and the Data board was edited to match.
- **Contrast.** Every level, singletons included, reaches 3:1 non-text contrast on every stage and
  on the image frame's blank screen field (owner, 2026-10-15: option B of mote
  bd-01M4SJ6T6MMGAW1PRGREGVSX50; quiet variant, 2026-10-16). The density keeps one ramp for every
  stage: level 1 keeps ramp-0 (owner, 2026-10-12), and the cells are drawn opaque. The 0.6 density
  opacity is retired for this picture; the mass maps keep 0.6 (§12).
  - **Where.** Casing is decided per level and per ground, not per stage. An edge between an
    occupied cell and an empty cell lies on one ground: the stage outside the image frame, or
    `--screen` inside it. Edges are split where the frame's boundary crosses them. A part is cased
    only where its level's opaque fill is below 3:1 against that ground. Edges between two occupied
    cells are level against level and are never cased, and the screen's border is not a ground.
  - **Band.** A cased edge wears one band, 1 logical px wide, outside the cell: the stage `--halo` or
    the inner casing (`TokenUsage.innerCasing`), whichever reaches 3:1 against that ground, and the
    higher contrast if both do. It is stroked under the fills, so only the outside half shows.
  - **Derived.** `DensityCasing.band(level, stage, ground)` computes both choices from the tokens, so
    a token change re-derives them. With today's tokens:

    | stage | on the stage | on the screen |
    |---|---|---|
    | Dark | ≥64 (1.50:1), halo 17.40 | 1–3, 4–15, 16–63 (2.17, 1.20, 1.82), inner casing 5.07 |
    | Mid | 4–15, 16–63, ≥64 (1.94, 1.13, 2.56), halo 4.54 | 1–3, 4–15, 16–63, inner casing 5.07 |
    | Light | 1–3, 4–15 (1.16, 2.09), halo 14.92 | 1–3, 4–15, 16–63, halo 5.92 |

    Every other pair reads on its own: on the stage, Dark 1–3 to 16–63 (13.38, 7.43, 3.39), Mid
    1–3 (3.49) and Light 16–63 and ≥64 (4.58, 10.38); on the screen, ≥64 (4.12). On the screen,
    white `--halo` is only 2.82:1, which is why Dark and Mid use the inner casing there.
  - **Order.** Adjacent levels are at least 1.80:1 apart (1.80, 2.19 and 2.27), and their luminance
    falls with the level, so the order survives greyscale. `TokenContrastSuite` and
    `GeometrySceneSuite` pin these values.
- **Semantics.** "{n} cells drawn at four log-spaced levels: 1–3, 4–15, 16–63 and at least 64
  records per cell." The ranges are the key's.
- **Empty and single-cell studies.** If no record falls on the screen (no placed records, or all
  of them off screen), there is no median. The step is 4, no cell is drawn, the key still shows
  "1–3" to "≥64" (owner, 2026-10-12), and the semantics text reads "0 cells drawn". With one
  non-empty cell, `m` is that cell's count. One record gives s = 4 and level 1. 300 records give
  s = 256, so the levels start at 1, 256, 1,024 and 4,096, and the cell is at level 2.
